# AI 開發規範

本文件規範 AI agent 如何製作遊戲。適用對象是在 VS Code 裡執行的 Claude Code，也適用於任何能執行終端機指令的 agent。

本專案的目標：使用者只要把故事交給 AI agent，AI 就能幾乎不靠人工，做出一款 **1～2 小時、分章節、好玩、可以從頭玩到結局** 的 RPG。為了避免一次產出大量品質差的內容，製作**以章為單位**進行；每一關都由**程式判定**，AI 不能以「我覺得完成了」為理由往下走。

---

## 1. 核心原則

0. **故事優先**：市面上好玩的 RPG，最後都歸結於故事好。`designGuide.ts` 的 **P 段（故事的靈魂）是主角**，A～H 只是輔助與安全網。不要為了逐條符合規則而把故事寫得僵硬、好猜；規則和「好玩」衝突時，以 P 為準，並在大綱裡說明理由。審查也照這個順序評分（盲猜測試、玩家評審團，見第 3 節）。
1. **只透過 Studio 操作 API 修改遊戲**：用 `npm run game -- [remote] apply`，不手動改寫 `project.json`。Studio 介面背後用的是同一套操作，人和 AI 的成果完全相容。
2. **先有好故事，才動工**：劇本大綱必須先通過獨立 AI 審查（`review-treatment`），否則 `apply` 會被擋下。
3. **一次只做一章**：新增下一章（`chapter.upsert` 新章節）之前，上一章必須通過章節審查；一次也只能新增一章。這兩條都由 CLI 強制。
4. **小步前進**：每批操作最多約 40 筆，送出後立刻 `check`，把 `validation.errors` 清空再繼續。
5. **程式說了算**：能不能玩看 `check`（驗證、整體與每章自動試玩、品質指標）；好不好玩看 `review`（獨立 AI 審查）。全部通過才能 `publish`。
6. **向玩家學**：開始製作與每一章動工前，先執行 `remote lessons` 讀取 AI 案例庫（`content/lessons.md`）。案例庫彙整了玩家玩完每一章留下的星等、標籤、評語，前台的匿名遊玩數據（每章完成率、實際花費時間、玩家最常放棄的地圖），以及歷次審查最常退件的問題。完成率低或常被放棄的地方，代表引導不清楚或節奏拖沓，擴充或製作新章時要優先處理。寫大綱與每一章時，主動避開裡面的問題，延續玩家喜歡的地方。審查員也會拿到同一份案例庫。
7. **送審前先自我檢查**：大綱與每一章送審前，對照 `designGuide.ts` 的評分標準逐項自我檢查，並在 treatment.md 最後附上「自我檢查表」，寫明每一項如何達成。審查會收斂：重審時審查員會先判定上一輪的問題是否已解決，所以修改時要逐條處理上一輪的意見。
8. **向前輩學，不憑直覺**：敘事設計準則（`src/ai/designGuide.ts`，A～H 與常見盲點 X）以業界設計者公開的方法為依據，出處見 `docs/narrative-design-guide.md`。寫大綱與每一章之前都要重讀 H 與 X。
9. **只使用素材庫裡的素材**：用 `npm run game -- assets` 列出可用的地形字元（村莊／城市營區／室內）、角色圖、圖示與音樂，依名稱與標籤挑選；不得虛構素材或授權。現代題材用城市地形與 `char_modern_*` 角色，室內場景用室內地形（物件會自動疊在木地板或水泥地上）。
10. **不抄襲**：參考網路上的資料時，只取共同經驗、題材或設計原則；不得改寫特定作品的情節或台詞，也不得使用真實人名或能辨識出特定個人的事件。

## 2. 兩種工作模式

| 模式 | 什麼時候用 | 指令 |
|---|---|---|
| **遠端模式**（建議） | `.env.local` 有設定 `STUDIO_URL` 與 `STUDIO_TOKEN` | `npm run game -- remote …` |
| 本機模式 | 沒有 Studio 帳號，只在 repo 裡製作 | `npm run game -- …` |

遠端模式：

- 使用者可能已經在 Studio 寫好故事。開始前先執行 `remote story <id>`，故事會存到 `content/<id>/story.md`。
- 故事、大綱與審查結果都會上傳到 Studio 的「製作看板」，使用者可以即時看到你做到哪一關、審查怎麼評。關卡以 Studio 上的審查紀錄為準。
- `remote apply` 會自動帶上目前的版本號。如果使用者剛好在 Studio 裡改了東西，會收到 409 衝突；這時先 `remote pull`，重新讀取後再操作。**不得強制覆蓋使用者的修改。**
- API Token 不能典藏專案，也不能略過品質指標與審查關卡發布。
- REST API 的說明見 `<STUDIO_URL>/api/docs`，操作的 JSON Schema 見 `<STUDIO_URL>/api/ops-schema`。

## 3. 製作流程

遊戲原始檔放在 `content/<id>/`：`story.md`、`treatment.md`、`project.json`、`reviews/`。下表的指令以遠端模式為例；本機模式拿掉 `remote` 即可。

| 階段 | 動作 | 關卡（不通過不能往下走） |
|---|---|---|
| 0. 建立 | 先 `remote lessons` 讀案例庫。使用者給的是專案 ID：`remote story <id>`；給的是故事：`remote create <名稱>`，再把故事寫進 `story.md` | — |
| 1a. 提案 | 使用者沒有給完整故事時：`npm run game -- seeds` 抽種子，寫 `pitches.md`：8～12 個一句話提案（格式見第 5 節），每個都標出它避開了老套清單的哪幾條；自己淘汰到剩 3 個 | 3 個提案交給**使用者挑選**（或混合）；使用者明確說「你決定」時才自己選，並寫下理由 |
| 1b. 故事 | 把選定的提案（或使用者的一句話）擴寫成 800～2000 字的 `story.md`：主角、渴望、衝突、世界、2～3 位核心人物 | — |
| 1c. 招牌場景 | 先寫出整款遊戲最想讓玩家截圖或跟朋友講的那一幕（約 1 頁，寫在 `treatment.md` 劇透線以下的第一段） | 把這一幕給使用者看一眼；不動人就回到 1a，不要硬做 |
| 2. 劇本大綱 | 依第 5 節的格式寫 `treatment.md`（4～6 章），用**劇透線**分成「玩家在第 1 章結束前會知道的事」與後面的真相 | — |
| 3. 大綱審查 | `remote review-treatment <id>`：先做**盲猜測試**（另一位 AI 只看劇透線以上的內容猜後面的劇情），再由審查員與**玩家評審團**評分 | `passed: true`；核心翻轉被猜中就重寫翻轉；最多 3 輪 |
| 4. 骨架 | 建立資料庫：角色（含角色設定與講話聲）、主要物品、任務、結局（先寫標題與方向）；第 1 章用到的地圖 | `check` 沒有驗證錯誤 |
| 5. 逐章實作 | 每章依序做下面 a～e，做完一章才開始下一章 | — |
| 5a. 開章 | `chapter.upsert` 新增這一章，設定 `testStart`（照主線玩到本章開頭時的位置、開關、物品、任務） | 上一章審查已通過（CLI 強制） |
| 5b. 內容 | 這一章的地圖、事件、對話、調查點、支線；章末用 `chapter` 指令進入下一章（最後一章用 `ending`） | — |
| 5c. 章節試玩 | `remote check <id>`，看 `chapters[]` 中這一章的結果 | 這一章 `ok: true`，時長 10～25 分鐘（8～30 分鐘以外會被擋） |
| 5d. 章節審查 | `remote review <id> --chapter <章節ID>` | `passed: true`；沒通過依意見修改後重審，最多 3 輪 |
| 6. 收尾 | 補完結局文字與尾聲（回應各章的主要選擇）、封面、開場文字 | `check` 的 `ok: true`：全長 60～120 分鐘、3～8 章、每章與每個結局都玩得到 |
| 7. 整體審查 | `remote review <id>` | `passed: true`，而且是針對目前這一版內容 |
| 8. 發布 | `remote publish <id>` | 以上全部通過（CLI 與伺服器都會檢查） |

**連載推出（建議）**：不必等全部章節完成。在系統設定把推出方式設為「連載中」（`project.update` 的 `release: {status: "ongoing", plannedChapters: N}`），最少 1 章就可以發布。
- 每一章的章末用「未完待續」結局收尾，也就是 `ending.upsert` 設定 `nextChapterId`。
- 下一章推出後，玩家的存檔會從那一章的開頭接著玩。
- 連載中只檢查每一章的試玩、時長與章節審查；全部完成後改成 `complete`，再做全長檢查與整體審查。
- 已推出的內容只能新增、不能刪改 ID（見第 8 節）。

隨時可以用 `remote status <id>` 查看卡在哪一關，用 `remote inspect <id>` 讀取目前內容（RPG Maker 式的事件清單）。

**依使用者的修改清單修正**：使用者在 Studio 測試遊玩時按「📌 標記修改」留下意見。`remote notes <id>` 列出待處理的意見，每一筆的 `at` 是位置代碼（`地圖/事件/p頁#指令路徑`）指到的指令。一次處理一筆：修改 → `check` → `remote resolve <id> <noteId> --reply "怎麼改的"`。使用者用文字描述位置時，用 `remote refs <id> <關鍵字或 ID>` 找出位置代碼；改共用的 ID 前也先用 `refs` 找出所有用到的地方。

**任何一個審查修改 3 輪後仍然不通過：停下來回報使用者**，附上審查意見。不得自行放寬門檻、刪掉章節或縮短遊戲來規避。

## 4. 品質門檻（由程式強制）

| 項目 | 標準 | 來源 |
|---|---|---|
| 結構 | 引用都存在、地形與事件位置正確、標籤存在、自動執行會關閉自己、共用事件沒有循環 | `validate.ts` |
| 可玩 | 從開頭能玩到每個結局，沒有卡死；每一章從測試起點能玩到下一章 | `playtest.ts`、`chapters.ts` |
| 時長 | 全長 60～120 分鐘；3～8 章（建議 4～6 章）；每章 8～30 分鐘（建議 10～25 分鐘） | `quality.ts` |
| 規模 | 人物 3～40 位、結局 2～4 個、可調查的事件至少 2 個、有後果的選項至少 3 個 | `quality.ts` |
| 敘事 | 沒有死開關、結局由至少 2 個條件或選擇決定、各結局路線的選擇不同 | `quality.ts` |
| 內容品質 | 總分 ≥ 7、每個面向 ≥ 6、沒有 critical、major 最多 3 個 | `review.ts`（大綱、章節、整體三種獨立審查） |

## 5. 劇本大綱格式（`treatment.md`）

大綱是給審查員看的設計文件，要寫清楚**為什麼好玩**，不只是劇情摘要。

提案（`pitches.md`）每一個都用這個格式，寫不出來就代表這個點子還不夠：

```markdown
## 提案 N：名稱
- 一句話：違反常識的世界規則或被反過來的老套（P1）＋主角的處境
- 主角想要什麼／最怕什麼
- 招牌時刻：玩家會跟朋友講的那一幕（一句話）
- 最大的翻轉：玩家以為……，其實……（回頭看伏筆在哪）
- 情緒核心：一個沒有標準答案的問題（P3）
- 語氣：例如「荒謬喜劇包著很痛的核心」（P5）
- 避開了哪些老套（CLICHES 的編號），像不像某部既有作品（像的話差在哪）
```

大綱格式：

```markdown
# 遊戲名稱
一句話：……
主題：……（例如「承諾的重量」）
核心問題：……（玩家在第一章結束前就會想知道答案的問題）

- 開場鉤子（H1）：前 3 分鐘發生什麼、主角想要什麼、角色怎麼說出最終目標與第一個小目標

- 名稱（定位）｜想要：……｜說話風格：……
```

## 6. 資料模型與操作 API（RPG Maker 式）

遊戲資料以 RPG Maker（MZ）的模型為基底，定義在 `src/game/schema.ts`：

- **資料庫**：`actors`（角色：名稱、角色圖、講話聲、角色設定）、`items`、`quests`（任務日誌：步驟清單）、`endings`（結局＋尾聲）、`chapters`（章節＋測試起點）、`commonEvents`、`switches`、`variables`、`system`（起點、主角、初始物品）。
- **地圖**：`maps[]`，地形是字元陣列（見 `TERRAIN`），`parentId` 形成地圖樹，地圖上放 **事件**。
- **事件**：`{id,name,x,y,pages[]}`。系統使用「條件成立、編號最大」的那一頁。每頁有：
  - `conditions`：`switches`（最多 2 個，皆 ON）、`variable {id,min}`、`selfSwitch`、`itemId`、`quest {questId,status}`、`custom`（任意條件）
  - `graphic {assetId}`（沒有＝透明事件）、`trigger`（`action` 確定鍵／`touch` 接觸／`autorun` 自動執行）、`priority`（`below`／`same`／`above`）
  - `commands`：事件指令列
- **事件指令**（`code`）：`text`、`choices`、`if`、`switch`、`selfSwitch`、`variable`、`item`、`quest`、`transfer`、`ending`、`chapter`、`common`、`erase`、`exit`、`label`、`jump`、`wait`、`music`、`comment`。

完整格式用 `npm run game -- schema` 或 `<STUDIO_URL>/api/ops-schema` 取得；`npm run game -- inspect <id>` 會把專案印成 RPG Maker 式的事件清單（◆ 指令）。

| 操作 | 用途 |
|---|---|
| `map.add` `{id,name,width,height,fill?,music?,parentId?}` | 新增地圖（外圍自動用樹圍起來） |
| `map.terrain` `{mapId,rows}` | 一次畫好整張地圖（每列一個字串，長度相同） |
| `map.paint`／`map.fill`／`map.resize`／`map.update`／`map.remove` | 局部繪製、填滿、調整大小、改名稱與音樂 |
| `event.upsert` `{mapId,event}` | 新增或整個取代事件（含所有事件頁） |
| `event.move`／`event.remove` | 移動、刪除事件 |
| `actor.upsert`／`item.upsert`／`quest.upsert`／`ending.upsert`／`chapter.upsert`／`commonEvent.upsert` | 資料庫（對應的 `.remove` 刪除） |
| `switch.upsert`／`variable.upsert` | 幫開關、變數取中文名稱（指令裡用到的 ID 會自動建立） |
| `system.update` `{start,playerActorId,initialItems}` | 起點、主角、初始物品 |
| `project.update` `{title,description,intro,genre,cover}` | 遊戲資訊與封面 |

### RPG Maker 的常見寫法

| 需求 | 做法 |
|---|---|
| 人物依劇情說不同的話 | 同一個事件放多頁：第 1 頁無條件，第 2 頁條件「開關 met_x ON」，以此類推（編號越大越優先） |
| 寶箱只能開一次 | 第 1 頁：文字＋`item`＋`selfSwitch A ON`；第 2 頁條件 `selfSwitch A`：「空的」 |
| 門／地圖出入口 | 透明事件、`touch`＋`below`，指令 `transfer`；雙向要兩邊各放一個 |
| 過場劇情 | `autorun` 頁，最後一定要 `selfSwitch A ON`（或關掉觸發它的開關），第 2 頁條件 `selfSwitch A` 留空 |
| 玩家的抉擇 | `choices` 的每個選項裡用 `switch` 記錄，之後用頁條件或 `if` 讀取（每個打開的開關都必須被讀取） |
| 任務日誌 | `quest start` → `quest step {step}` → `quest complete`；步驟文字寫「找誰／去哪／做什麼」 |
| 章節 | 劇情轉折處用 `chapter` 指令（顯示標題卡）；在資料庫為每章設定 `testStart`，可以直接從那一章開始測試 |
| 結局 | 在條件分支或事件頁條件裡用 `ending` 指令；結局至少由 2 個條件或選擇決定，用 `epilogues` 回應其他選擇 |

**新增時的順序**：先建立資料庫項目（角色、物品、任務、結局、章節），再放引用它們的事件。

## 7. 常見錯誤（審查最常退件的原因）

先對照 `designGuide.ts` 的 X1～X8（AI 常見盲點），再檢查下面這些：

1. **台詞與狀態不一致**：台詞說「給你」，卻沒有 `item` 指令；或還沒發生的事被說得像已經發生過（例如還沒見過村長，人物卻說「村長叫你來的吧」）。
2. **互斥的抉擇可以重複做**：選了 A 之後還能回頭選 B。解法是用事件頁條件或選項條件隱藏另一個選項。
3. **主要選擇在結局完全沒被提到**：用 `ending.epilogues` 回應。
4. **結局文字描述了玩家不一定經歷過的事**：結局文字只能寫這個結局的條件保證成立的事。
5. **假選擇**：選項的內容都一樣，或沒有任何開關記住。
6. **一條直線的跑腿**：「找 A → 開箱 → 開門」沒有轉折，也沒有第二種解法（H8、H9）。
7. **秘密太早說破或重複揭露**：同一個真相被兩個人物各講一次（X2、H6）。
8. **鎖住的東西沒有提示解法**：「門鎖著」之後必須提示要找誰、去哪（G2、H17）。
9. **情感高點後馬上切章**：拿到關鍵物品後立刻跳出章節標題卡，沒有讓玩家消化的停頓（E2）。

## 8. 已上線遊戲的更新與擴充

- 已發布的遊戲**不得刪除或改名**既有的 ID，包括地圖、事件、角色、物品、任務、章節、開關和變數。玩家的存檔會用到這些 ID。
- 新內容只能**新增**。要改變劇情時新增事件頁（編號更大的頁會優先），舊頁保留。
- 擴充內容用新的地圖與章節，透過新的場所移動或「通關後才出現」的事件頁接上原本的遊戲；新章節同樣要通過章節審查。

## 9. 回報格式

完成或停下來時，請回報以下內容：

- 遊戲 ID 與名稱
- 預估時長（全長，以及每一章）
- 章節數與結局數
- 各次審查的分數（大綱、每一章、整體）
- 如果沒有通過：失敗的關卡，以及審查意見
- 發布狀態
